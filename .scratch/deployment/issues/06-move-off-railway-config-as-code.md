# 06: Move the server and web services off Railway config as code

Read `../spec.md` first, and `docs/adr/0010-protected-main-and-gated-deploys.md`
(Railway waits for CI).

**What to build:** Before Railway stops reading `railway.json` on
2026-12-01, the api and web services keep every setting their config files
apply today, through whichever replacement fits: Railway's Infrastructure as
Code (`.railway/railway.ts`, applied with the Railway CLI) or the dashboard.

**Blocked by:** none

**Status:** ready-for-human

**Notes:** Found on 2026-10-18 while writing production-backups 04, whose
`backup` service uses dashboard settings because new services cannot opt
into config as code
(`../../production-backups/issues/04-nightly-backup-job.md`, Comments).
Railway's docs (`infrastructure-as-code.md` in `railwayapp/docs`) mark config
as code deprecated and name 2026-12-01 as the hard cutoff. Railway's
`railway config migrate` writes a `.railway/railway.ts` from the existing
files. From the docs read so far, the IaC `service()` options have no restart
policy, Dockerfile path or draining time, so some settings may have to move
to the dashboard instead. A settings change that only lives in the dashboard
leaves no record in the repository, so whatever moves there is written down
somewhere in the repository.

What the files apply today:

- `apps/server/railway.json`: Dockerfile builder, `dockerfilePath`, eight
  watch patterns, health check `/health`, restart policy `ON_FAILURE`,
  `drainingSeconds: 10`.
- `apps/web/railway.json`: Dockerfile builder, `dockerfilePath`, nine watch
  patterns (including `/apps/server/**`), health check `/`, restart policy
  `ON_FAILURE`.

**Research findings**

- Scope is the `api` and `web` services only. `apps/backup` has no
  `railway.json` and already uses dashboard settings.
- The tentative note above is half right. Railway's IaC docs do not document
  builder, `dockerfilePath`, watch patterns, restart policy or draining time.
  The TypeScript SDK and CLI do accept them (`build.builder`,
  `build.dockerfilePath`, `build.watchPatterns`, `deploy.restartPolicyType`,
  `deploy.drainingSeconds`). Only the health check path is documented.
- `railway config migrate` carries builder, `dockerfilePath`, watch patterns
  and health check path, and by the agent's reading of the CLI source it
  drops `restartPolicyType` and `drainingSeconds` silently. Not run.
- Not tested: whether `apply` writes `restartPolicyType` and
  `drainingSeconds` to a live service.
- `plan` and apply run locally with the owner's login; no CI secret is
  needed. ADR 0010 does not itself ban cloud credentials in CI (it requires a
  read-only workflow token and required checks); the nearest written rule is
  ADR 0013 about AWS credentials. Do not use the `railwayapp/config` Action
  or a `RAILWAY_TOKEN` secret.
- At the cutoff the docs say only that the files "stop being read". They are
  silent on freezing, resetting or copying values. The likely outcome (an
  inference) is a Railpack build with no health check. Doing nothing is not
  safe.
- Wait for CI is a service setting, not a `railway.json` one, and survives
  the cutoff. If `railway.ts` declares `source`, it would own that flag.
- `railway config migrate cutover` clears the Config File path, redeploys and
  saves an undo snapshot (`migrate undo` reverses it). `plan` is blocked for
  a service still on `railway.json`, so run `cutover` just before the final
  apply. The docs and changelog disagree on whether `migrate --apply` alone
  clears the path.
- A single merged `railway.ts` deletes omitted resources; review the plan so
  it leaves the `database` and `backup` services alone.
