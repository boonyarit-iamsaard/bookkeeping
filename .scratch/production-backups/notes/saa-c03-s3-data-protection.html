SAA-C03: S3 data protection and budgets

The exam view of the ground tickets 02 and 03 covered: keeping objects from being exposed, overwritten or deleted, encrypting them, expiring them, and capping what it all costs. Most of it sits in domain 1, Design Secure Architectures; the backup and retention parts reach into domain 2, Resilient Architectures, and lifecycle and Budgets into domain 4, Cost-Optimized Architectures. Each part uses this project's backup bucket as the example. It follows the identity sheet; the operational record is the ticket 03 runbook.

Versioning and how deletes really work

A bucket is unversioned (the default), versioning-enabled or versioning-suspended. Once enabled, it can never return to unversioned, only be suspended. Objects stored before versioning keep the version ID null. Every version is a whole object and is billed as one.

Request Versioned bucket Under Object Lock retention
PUT an existing key A new current version; the old one becomes noncurrent Allowed; the locked version stays locked
DELETE without a version ID 200, and a delete marker becomes the current version. Nothing is removed. Same: 200 and a marker
DELETE with a version ID That version is permanently removed 403 Access Denied

MFA Delete adds an MFA code to two requests: changing the versioning state and permanently deleting a version. Only the bucket owner's root user can enable it, through the CLI or API and never the console, and it cannot be used together with a lifecycle configuration.

Worked through this project

The uploader tries aws s3 rm on the probe

It is refused before versioning matters: the uploader has no s3:DeleteObject, so IAM says no identity-based policy allows the s3:DeleteObject action. Had it held that permission, the delete would have succeeded by adding a delete marker, and the backup would still have been there underneath.

The owner deletes the probe by its version ID

AdministratorAccess allows s3:DeleteObject, and S3 still answered Access Denied because object protected by object lock. The test had to name the version ID: a plain aws s3 rm would have returned success and proved nothing.

Object Lock

Protection Who can remove it early Use it when
Compliance mode Nobody, not even root. The mode can't change and the period can't shorten. The only way out is closing the account. Regulations (SEC 17a-4 style) or ransomware-proof backups
Governance mode Anyone with s3:BypassGovernanceRetention who sends the bypass header; the console sends it automatically Testing retention, or WORM with an emergency override
Legal hold Anyone with s3:PutObjectLegalHold No known end date; independent of any retention period
Variable retention newer As its mode; the clock starts when the event hold is released Retention that begins at a future event, such as account closure
  • Object Lock needs versioning. Once on, neither Object Lock nor versioning can be turned off. It can now be enabled on an existing versioned bucket, not only at creation.
  • A bucket's default retention gives every new version a retain-until date of its creation time plus the period. An explicit retention on the PUT overrides the default.
  • Retention protects a version, not a key: new versions and delete markers can still be added on top. Delete markers themselves are never protected.
  • Uploads that get a retention period must carry Content-MD5 or an SDK checksum header. Current SDKs and CLI v2 send a CRC checksum by default.
  • A bucket with Object Lock can't be the destination for server access logs.

Lifecycle

Lifecycle rules act on a prefix or tag filter. On a versioned bucket, each kind of action does a different job:

Action What it does Here
Expiration Adds a delete marker to the current version; on an unversioned bucket it deletes the object daily/ 35 days, monthly/ 365 days
Noncurrent version expiration Permanently deletes versions some days after they became noncurrent. Without it, expiry on a versioned bucket keeps every version forever. 1 day
Expired delete marker cleanup Removes markers with no versions left behind them On
Transition Moves objects to a cheaper storage class None; the dumps are tiny

Lifecycle never deletes a version that is still locked; it waits. Transitions only go down a waterfall towards colder classes, and never back up. Standard can go to any colder class. One Zone-IA can go only to Glacier Flexible Retrieval or Deep Archive, Flexible Retrieval only to Deep Archive, and Deep Archive nowhere. Moving an archived object back up takes a restore and a copy. By default, objects under 128 KB don't transition at all, because the per-object request would cost more than it saves. Leaving a class before its minimum duration is billed as if the object had stayed.

Storage class Minimum duration Minimum billed size Access
Standard None None Milliseconds, 3+ AZs
Intelligent-Tiering None None (under 128 KB stays in Frequent Access) Milliseconds; monitoring fee, no retrieval fee
Standard-IA 30 days 128 KB Milliseconds; retrieval fee
One Zone-IA 30 days 128 KB Milliseconds; 1 AZ, so only for re-creatable data
Glacier Instant Retrieval 90 days 128 KB Milliseconds; for data read about once a quarter
Glacier Flexible Retrieval 90 days 40 KB metadata overhead per object Restore first: minutes to hours
Glacier Deep Archive 180 days 40 KB metadata overhead per object Restore first: hours

Encryption

Option Who holds the key Pick it when
SSE-S3 S3, per-object keys under a rotated root key; AES-256 Default for every bucket since 2023, free. Enough when nobody needs to audit key use.
SSE-KMS AWS KMS: an AWS managed key or a customer managed key You need a key policy, CloudTrail records of key use, or cross-account access. Only a customer managed key can be shared across accounts.
DSSE-KMS KMS plus S3, two independent layers A compliance rule demands two layers of encryption
SSE-C changed You send the key with every request Rarely. Since April 2026 it is blocked by default on new buckets and must be turned on deliberately.
Client-side You, before upload AWS must never see plaintext
  • SSE-KMS permissions: uploads need kms:GenerateDataKey and downloads kms:Decrypt, on top of the S3 permissions. A missing KMS permission fails the S3 request, so check both.
  • S3 Bucket Keys cut KMS request costs by up to 99%, by using a bucket-level key to make data keys.
  • Changing default encryption doesn't re-encrypt existing objects; S3 Batch Operations with a copy does.
  • The KMS key must be in the bucket's Region. A server access log destination bucket must use SSE-S3.

Why this bucket uses SSE-S3, not KMS

The dumps are age-encrypted before they leave Railway, so only the owner's private key can read them, whatever happens to AWS. SSE-S3 adds encryption at rest for free. A customer managed KMS key would cost money and protect nothing the client-side encryption doesn't. The spec rules it out.

Block Public Access and Object Ownership

Setting Effect
BlockPublicAcls Rejects requests that set a public ACL
IgnorePublicAcls Ignores public ACLs that already exist
BlockPublicPolicy Rejects a bucket policy that would grant public access
RestrictPublicBuckets If a policy is public anyway, only AWS services and the owner's own account may use the bucket; all cross-account access stops
  • Settings exist at the organization newer, account, bucket and access point level. S3 applies the most restrictive combination, so a bucket can't opt out of an account setting.
  • The settings never edit policies or ACLs. Turning one off makes whatever was public public again.
  • A policy counts as public unless it limits access to fixed principals, accounts, VPCs, endpoints or narrow IP ranges.
  • Object Ownership: bucket owner enforced (the default) turns ACLs off and gives the bucket owner every object; bucket owner preferred and object writer keep ACLs. Keep ACLs off unless each object needs its own access.

AWS Budgets

  • Types: cost, usage, RI utilization and coverage, and Savings Plans utilization and coverage. Periods are daily, monthly, quarterly, yearly or a custom range.
  • Monitoring and alerts are free. Budget actions are free for the first two action-enabled budgets, then $0.10 a day each.
  • Alerts fire on actual or forecasted spend. An actual alert fires once per period; a forecast alert can fire again if the forecast dips and climbs. Forecasts need about five weeks of usage data.
  • Each alert goes to up to 10 email addresses and one SNS topic, in the budget's own account. An SNS topic needs a policy that lets budgets.amazonaws.com publish.
  • Billing data refreshes up to three times a day, so an alert can arrive after the threshold has already been passed. A budget warns; only a budget action, such as applying a deny policy or an SCP, stops spending.
  • A member account can create budgets for itself. The management account can track any member's costs, but its budgets stay invisible to that member.

This project's budget

A $1 monthly cost budget in backups, emailing the owner at 80% actual and 100% forecast. Both alerts email the owner directly, so there is no SNS subscription to confirm. The forecast alert can't fire before about five weeks of usage, late November 2026.

From the run

A name nobody else can take newer

Bucket names share one global namespace, and a deleted name can be claimed by another account, which then receives requests meant for you. The account regional namespace (names ending -<account id>-<region>-an) can only ever belong to one account. It is new enough to be unlikely on the exam; the global uniqueness rule is not.

Least privilege needs no deny

The uploader's only policy allows s3:PutObject on two prefixes. List, read and delete all failed with "no identity-based policy allows", which is an implicit deny. Note that aws s3 cp to stdout fails on HeadObject, which also needs s3:GetObject.

Look before an irreversible create

The stack was first deployed as a change set (--no-execute-changeset) and read back before it ran. Once an Object Lock bucket exists, neither the lock nor the name can be undone.

Trap statements

Decide true or false, then open each one to check.

Deleting an object in a versioned bucket without a version ID removes it permanently.

False. It adds a delete marker. Every version is still there, and deleting the marker restores the object.

Versioning can be turned off once enabled.

False. It can only be suspended. With Object Lock on, it can't even be suspended.

Under compliance mode, root can shorten the retention period.

False. Nobody can shorten it or change the mode. It can only be extended.

Object Lock can only be enabled when a bucket is created.

False, now. It can be enabled on an existing versioned bucket. Older study material says otherwise.

A legal hold expires after a set number of days.

False. It has no end date and stays until someone with s3:PutObjectLegalHold removes it.

A lifecycle expiration rule can delete a version still under Object Lock retention.

False. It can add delete markers, but the locked version stays until its retention ends.

MFA Delete can be enabled by an IAM administrator in the console.

False. Only the bucket owner's root user can, and only through the CLI or API.

Default bucket encryption also protects data in transit.

False. It covers data at rest. In-transit protection is TLS, enforced with a deny on aws:SecureTransport false.

SSE-KMS with the AWS managed aws/s3 key lets another account read the objects.

False. Cross-account access needs a customer managed key whose key policy allows the other account.

A user with s3:GetObject can always download an SSE-KMS object.

False. They also need kms:Decrypt on the key.

Turning off Block Public Access leaves the bucket as private as it was.

False. The settings only override policies and ACLs; they don't edit them. Anything public underneath becomes public again.

A bucket-level Block Public Access setting can override a stricter account-level one.

False. S3 applies the most restrictive combination across levels.

Transitioning 50 KB objects to Glacier Deep Archive saves money.

False, usually. Each archived object adds 40 KB of metadata and a transition request, so by default objects under 128 KB don't transition at all.

One Zone-IA is a good home for the only copy of backups.

False. It lives in one Availability Zone. Use it only for data you can re-create, such as a replica.

An AWS Budgets alert stops further spending.

False. An alert only notifies. A budget action, such as attaching a deny policy or an SCP, is what restricts.

A forecasted-spend alert works from the first day of a new account.

False. Budgets needs about five weeks of usage before it can forecast.

Cross-Region Replication needs versioning on both buckets.

True. Source and destination must both be versioning-enabled.
