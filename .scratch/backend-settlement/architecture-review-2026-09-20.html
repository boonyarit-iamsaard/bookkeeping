The primary seam is the application function interface (db: Database, input) ⇒ Promise<Result<T, E>>, crossed by two adapters (Hono, web actions). It is a real seam and already deep: createTransaction hides locking order, savepoints, idempotency and eleven validators behind one call. The friction below is at the edges of that seam — what the error values carry, what the receipt stores, what each adapter must re-derive — not in the middle of it.

Same shape as WalletOpeningIssue. One field vocabulary per operation, owned where the rule is evaluated.

Problem
Which input a rejection addresses is decided in two adapters via exhaustive switches, and they already disagree (`wallet-archived` gets a pointer in Hono, no field in web).
Solution
Transaction rejections carry field like wallet and category issues do; both adapters collapse to lookup tables. Adding a code touches the application file, not three.
Wins
  • locality: field choice lives with the rule
  • leverage: SPA gets the table for free
  • delete 80 lines of Exclude<> switches
  • tests: route suite keeps D2 scope, asserts a table
  • one rejection shape across the package

2 · One pure transaction acceptance module

Strong in-process test-suite-health D9

packages/application/src/transactions/transaction.ts:468 validateTransactionValues · :563 validateRefundShape · :576 validateTransferShape · :635 validateRefundAgainstExpense · :731 validateTransactionDate · :883 snapshotOf · :900 sameSnapshot · :969 inline after-snapshot · :1112 guardRefundedExpense

Before — rules interleaved with locks

validateTransactionValues pure
executeIdempotentCreation → db.transaction I/O
validateTransferShape / validateRefundShape pure
lockRefundedExpense I/O · lock order
lockOwnedWallets (+ archived / retained rule) I/O + rule

validateTransactionDate pure
validateRefundAgainstExpense (currentRefundsOf + cap) I/O + rule

Every pure rule is only reachable through Postgres. One rule change → 2 918 lines of integration tests are the nearest oracle.

After — load facts, accept, persist

shell: lock expense → lock wallets → read category → read refunds I/O, ordered
acceptTransaction(fields, facts, today) shape · currency · amount · note · date bounds · before-opening · archived/retained · category kind · refund cap · expense guard · snapshot equality ⇒ Result<AcceptedTransaction, TransactionRejection>
shell: insert · write change · read back I/O

Facts = { wallets[{id, openingDate, archivedAt}], category?, expense?, existingRefunds[], current? }. Create and update call the same acceptance once.

Problem
Nine private validators are woven between locks, so reading “what makes a transfer acceptable” means walking the I/O path, and no rule has a unit test. sameSnapshot already drifted (omits refundOfTransactionId; latent, since updates fix the link).
Solution
One pure module with one interface: fields + loaded facts in, accepted command or field-addressed rejection out. The shell keeps lock ordering and persistence and stays integration-tested for exactly that.
Wins
  • interface: one function, one test surface
  • tests: rules run in ms, no container
  • locality: create and update share one acceptance
  • integration suites shrink to lock/ownership/persistence
  • pairs with #1: the rejection shape is the output type
ADR-0004 assigns “use cases and business invariants” to @bookkeeping/application. Placing this module in application/transactions/transaction-rules.ts respects that and still needs no Postgres; placing it in @bookkeeping/domain (as D9 suggested) reopens that line. Worth deciding in the grilling, not by default.

Problem
The idempotency module is deep, but every caller undoes it: hand-mirrors its result type into a codec, unwraps and rewraps the outcome, and re-branches on the conflict code. Adding a field to TransactionDetail means editing the codec or silently breaking replay.
Solution
The module owns a generic JSON-safe snapshot (bigint/Date aware) and returns replayed inside the same Result; feature modules pass only scope, payload and create. Retire the dead findReplayedTransaction seam. Hard-deleted wallets keep the snapshot approach justified (re-reading is not an option for them).
Wins
  • delete ~180 lines of type mirroring
  • locality: snapshot format in one module
  • leverage: next creating operation is free
  • tests: round-trip cases in idempotency.unit.test.ts
  • removes 5 conflict re-branches

Problem
Deleting an expense with refunds and removing a protected / in-use category return a bare 409; the domain reason only survives in the temporary web adapter. The SPA would have to reinvent that read against a contract that hides it.
Solution
Problem details carry the domain code (refunds-exist, protected, has-children, in-use) and a typed detail (refunds in Money wire form) — the ADR-0003 “stable machine-readable code” promise applied to 409s, not only 422 field errors.
Wins
  • interface: contract says why, not just no
  • leverage: SPA and mobile share one read
  • locality: reason formatted once, client-side
  • tests: one route case per code, contract schema for details
Consistent with ADR-0003 (“expected failures use stable machine-readable codes”); it widens the problem-details contract before the SPA consumes it, which is cheaper now than after.

After — glue in core/http, projection in the feature

respondWithResult(c, result, { created?, notFound, fieldPointers }) status choice · problem body · Location · conflict · field table (#1) · documented responses
feature: schema · toInput(c) · present(value)

Depends on #1: with field-addressed rejections the 422 branch needs a table, not a switch, so the helper can own it.

Problem
Route files are ~70 % glue: the same Result-to-response branching, Location header, session projection and explicit describeResponse generics appear 15+ times, so each new endpoint is copied from the last one.
Solution
A small deep helper in core/http that turns an application Result into the documented response; feature routes keep only schemas, the request→input projection, and presenters.
Wins
  • leverage: one helper, 15 handlers
  • locality: problem mapping in one module
  • route files drop ~40 %
  • tests: helper unit-tested; route suites unchanged in intent
Caution: hono-openapi cannot infer the describeResponse generics today (the comment repeats in every file). A helper that fights that inference is a shallow module in disguise; the grilling should prototype one create handler before committing.

Problem
The active-filter set that a cursor is bound to is declared once in domain, again (nullable) in the cursor module, and mapped between them in the route — a shallow mapper whose only job is ?? null.
Solution
The cursor codec accepts and returns the application's own list options; the route passes one object through. Small, self-contained; ranks low because nothing currently breaks.
Wins
  • delete two of three filter shapes
  • locality: adding a filter touches two files, not four
  • tests: cursor unit tests only

DDD assessment (per docs/agents/domain.md)

Concrete evidence of invariant drift: amount range, note length, calendar date, transfer shape and THB currency are each enforced in four places (application, HTTP schema, web form schema, Postgres check constraints); the before-opening date rule and the refund cap in two runtime places plus a client hint. The mutation check in facts.md already showed one rule turning seven tests red across three packages. No term has acquired conflicting meanings, and there is no second rule set needing separate ownership, so an aggregate or bounded context is not warranted.

Smallest practice that fits: a domain-owned invariant — candidate #2's acceptance module is exactly that. The HTTP and form schemas keep shape checks (they are the adapter's interface), the Postgres checks stay as a last line, but the rule gets one author and one unit-tested home. No new enforcement tooling; the existing Biome barrel and import rules already keep @bookkeeping/domain free of I/O.

Looked at, not proposed

  • Repository seam over Database — one adapter (Postgres). ADR-0004 says no; nothing has changed. Hypothetical seam.
  • Splitting transaction.ts by operation — 1 345 lines but one deep interface; splitting moves code without concentrating anything. #2 shrinks it for a reason instead.
  • validateWalletOpening / validateCategoryUpdate exported for tests — each has one caller; harmless, but the same pattern #2 does properly. Fold into #2's shape when touched.
  • invalid-currency / normalizeTransactionInput currency dance — unreachable over HTTP or the web form; deletes itself inside #2.

Top recommendation

#1 Rejections name their field, then #2 acceptance module as one track

#1 is the smallest change with two real adapters already paying for it, it unifies the three rejection vocabularies inside @bookkeeping/application, and its output type is what #2's pure module returns — so doing #1 first makes #2 a mechanical extraction instead of a design exercise. Together they close test-suite-health D9 and make #5's route helper possible. #4 is the one to do before the SPA consumes the contract; #3 and #6 are cleanups to schedule when those files are next open.
