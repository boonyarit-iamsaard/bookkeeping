## 3. Production restore: undecided, no spec yet

The drill proves a backup restores into a throwaway container. Nothing
documents how to bring production back from a backup, though ADR 0009 relies
on that to undo a bad migration, and `production-migrations` (the next spec)
depends on it. The production-backups spec excludes only automatic or
one-click restore.

The questions to settle with the owner:

1. Restore target: the same Railway Postgres, a new Railway database, or
   another provider after losing the Railway account (ADR 0008's reason for
   off-site backups).
2. Access: Postgres has no TCP proxy on purpose. Choose between a temporary
   proxy, `railway ssh`, or a one-off restore service inside the project.
3. Rows written after the backup: re-enter them, or dump the damaged
   database first and salvage them.
4. Order: stop the API, restore, check with the manifest comparison, restart.
5. Acceptable downtime. Up to a day of data loss is already accepted; the
   time to recover is not stated.

Proposed: grill the owner on these, then write a small spec with a runbook
and one rehearsal against a disposable Railway database, before
`production-migrations` starts. The owner has not agreed to start it yet.

  one argument. Run harness loops under `bash`.

  the S3 drill in their own terminal. The owner's identity has two copies, a
  password manager and a passphrase-encrypted cloud-drive copy (build log,
  ticket 01). Never print a private key.

  needs the owner's decision; trim stale text instead.

- Docker: remove throwaway Postgres containers with `-v`, because the image
  declares a volume. Before any `docker volume prune`, check what it will
  remove.
