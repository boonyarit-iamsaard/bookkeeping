Problem

The plan's interface exposes read mechanics; adding category spending and closing balances required matching edits to the loader, subscriptions, and ready-data guard.

Solution

Put required reads, preload/observe coordination, and comparison-result identity behind one feature-local module, keeping TanStack Query and the existing read adapter.

Depth & deletion test

The plan already earns its validation logic; absorb the repeated protocol rather than deleting that value. Deleting the deep module would scatter read inventory and comparison ordering back into callers.

Tests through the seam

Exercise valid/invalid addresses and delayed comparison changes through the module's interface; assert that totals remain visible and an old wallet's figures never acquire the newly chosen wallet's name.

  • Locality: one read inventory
  • Leverage: loader and screen
  • Depth: hide result ordering
Evidence, test coverage, and adapter discipline
  • report-queries.ts:7–18 publishes six named kinds of read handle; the loader manually visits them at routes/_app/reports.tsx:17–28, while the screen manually subscribes at reports.tsx:41–78 and checks availability at 134–140.
  • reports.tsx:23–28, 53–62, 145–148 strips wallet figures from placeholder data and chooses cached same-month totals. This is existing protective behavior; no stale-wallet defect was reproduced.
  • Commits 346f162, fa76bd3, and d6a31a5 demonstrate repeated changes to this protocol as level 3 reads arrive.
  • apps/web/tests/e2e/reports.spec.ts:15 covers real reads, month/date changes, comparison retention and clearing; :218 covers initial loading. It does not hold two successive wallet reads to check pending-result identity.
  • Keep the production HTTP adapter. Use delayed test responses only where they test observable ordering; two adapters justify that seam. Do not add a generic transport framework or put individual endpoint calls behind new pass-through modules.

Compatible with ADR 0006 and cached-read conventions: preserve path/parameter keys, centralized refreshAfterWrite, session resets, and accepted previous-data behavior.

Problem

The selection interface makes capture coordinate a local list with the live cache, while creation recovers a new Parent category from a read kept active elsewhere.

Solution

Give the Category selection module ownership of the current tree and create-to-select lifecycle, so capture receives the chosen category without reconstructing the tree.

Depth & deletion test

Deleting the manual append removes a second catalog but loses today's create-to-select ordering; absorbing that ordering behind the selection seam adds depth instead of merely moving the callback.

Tests through the seam

Create a Child category with a new Parent category under a delayed refresh; assert the chosen path, inherited hue, preserved capture values, and correct selection on reopening.

  • Locality: catalog and selection together
  • Leverage: capture stops reconstructing parents
  • Depth: own create-to-select ordering
Evidence, test coverage, and adapter discipline
  • transaction-form.tsx:365 reads live colors through useCategoryColors, but :372 snapshots initialCategories; :374–382 appends the creation outcome locally. :741–744 orders that append before selecting the saved category.
  • use-create-category-form.ts:174–186 explicitly assumes the categories list is on screen, awaits the global refresh, then recovers the created parent from cached data. use-category-colors.ts:11 supplies an active read in capture.
  • category-picker.tsx:29–38 requires categories, selection, and a creation outcome from its caller. This is a real caller protocol; the inferred risk is divergent paths/catalogs after refresh, not a confirmed production failure.
  • apps/web/tests/e2e/transaction-entry.spec.ts:301–334 covers creating a parent inline. The redesign ticket 06 records a manual parent/child scenario; the cited browser case does not assert that scenario.
  • Keep the existing HTTP read/write adapter and global cache refresh policy. Controlled test responses can provide the second adapter for timing; no application-owned business rule moves into capture.

Compatible with ADR 0005 and the redesign's stable Parent category hues. This is client read/selection ownership; it does not require a new domain term, schema, or category business-rule owner.

Problem

The interaction module's interface silently requires its caller to supply a reset key; the marker index can fall back while the readout still looks up the original selected date.

Solution

Keep default-day choice, reset/preserve behavior, and selection resolution inside the existing Closing balance interaction module, leaving geometry calculation as useful internal implementation.

Depth & deletion test

Removing the caller's key loses the existing reset behavior; concentrating that behavior locally makes it disappear from callers. Deleting the deep module would scatter selection knowledge again.

Tests through the seam

Keep keyboard and pointer browser assertions; cover Balance date changes, comparison loads, and a refreshed read without the selected date, requiring marker, announced date, and readout to agree.

  • Leverage: one resolved selected day

Evidence, test coverage, and adapter discipline
  • balance-trend.ts:144–146 selects the default; financial-report.tsx:188 resets using month + asOf; balance-over-time.tsx:201 copies that default only on mount.

  • This is a smaller optional follow-on to candidate 01. It can be tackled independently if selected-day interaction changes next; it does not need the Reports read module to absorb chart gestures.

Compatible with the level 3 default-day and comparison decisions: month/Balance date changes reset selection; comparison changes preserve the chosen day. ADR 0001's Closing balance calculation stays untouched.

Top recommendation

01 / Reports read module

Three recent report changes exposed the same caller protocol, so concentrating inventory, readiness, and comparison identity gives immediate locality and leverage while preserving the existing adapter and cache conventions.

Modules that already earn their keep

  • Category spending and Closing balance calculations. Keep the server-calculated reads and their current domain meanings. transaction.ts:1097–1188 already hides carry-in, daily accumulation, opening dates and owner checks; wallet.ts:94–111 shares wallet movement signs and transaction membership. Moving these files alone adds no depth.
  • Presentation derivations. createCategoryBreakdown and createBalanceTrend hide signed shares, gaps, scales and empty states behind useful interfaces. Their internal pure functions are not shallow merely because they are small.
  • Redesign extractions. The final sweep already extracted HeroSkeleton, AmountInput, MonthSections, and ConfirmPanel. It deliberately kept the two auth-form class strings and Reports' exact per-wallet text. Reopening those choices has no new evidence.
  • DDD assessment. No new conflicting domain meanings or demonstrated cross-operation invariant drift were found. ADR 0005's single-context, owned-rule approach remains sufficient; no aggregates, repositories, or separate reporting context are recommended. ADRs 0001, 0004, 0006, 0011 and 0012 remain compatible with these candidates.
